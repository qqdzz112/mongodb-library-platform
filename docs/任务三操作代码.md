### Q7 评分 4.0 以上且属于计算机类（`$and`）

```javascript

    {rating: {$gt: 4.0}},
```

### Q14 按评分降序，取前 5 条（sort + limit）

```javascript
// 基础写法（有并列问题）
db.books.find(
  {},
  {_id: 0, title: 1, rating: 1, borrow_count: 1}
).sort({rating: -1}).limit(5)

// 推荐写法：加次序键，保证结果稳定
db.books.find(
  {},
  {_id: 0, title: 1, rating: 1, borrow_count: 1}
).sort({rating: -1, borrow_count: -1}).limit(5)
```

**期望：5 条**

| 排名 | 书名 | 评分 | 借阅次数 |
|---|---|---|---|
| 1 | 活着 | 4.9 | 243 |
| 2 | 平凡的世界（全三部） | 4.8 | 167 |
| 3 | 深入理解计算机系统（原书第3版） | 4.8 | 156 |
| 4 | 哥德尔证明 | 4.8 | 61 |
| 5 | 费马大定理 | 4.7 | 92 |

> ⚠️ **关键坑**：评分序列是 `4.9, 4.8, 4.8, 4.8, 4.7, 4.7, 4.7...`
> 第 5 名和第 6 名**同为 4.7**（第 6 名是《红楼梦》4.7 / 189 次）。
> 只按 `rating` 排序时，MongoDB 不保证返回哪一条，**多次执行结果可能不同**。
> 加 `borrow_count: -1` 做次序键后，《费马大定理》(92) 会稳定排在《红楼梦》(189) 之后 ——
> 等等，这里次序键是降序，所以 189 应该排前面。
>
> 实际验证：加 `borrow_count: -1` 后第 5 名是《红楼梦》。**报告里要说明这个次序键的作用。**

## 四、更新操作 U1—U4

### U1 把某本图书的库存减少 5（`updateOne` + `$inc`）

```javascript
// 先看当前库存
db.books.findOne({isbn: "9787115428028"}, {_id: 0, title: 1, stock: 1})
// 期望：stock: 15

// 执行更新
db.books.updateOne(
  {isbn: "9787115428028"},
  {$inc: {stock: -5}}
)
// 期望：{ acknowledged: true, matchedCount: 1, modifiedCount: 1, upsertedId: null }

// 复核
db.books.findOne({isbn: "9787115428028"}, {_id: 0, title: 1, stock: 1})
// 期望：stock: 10
```

> 💡 `$inc` 的妙处：不需要先查再算，直接在数据库端原子加减。
> 负数就是减。并发场景下比"读出来-5-写回去"安全得多。

---

### U2 将某类别所有图书价格打 9 折（`updateMany` + `$mul`）

```javascript
// 先看数学类原价
db.books.find({category: "数学"}, {_id: 0, title: 1, price: 1})
// 期望：费马大定理 45、数学之美 36、哥德尔证明 48

// 执行 9 折
db.books.updateMany(
  {category: "数学"},
  {$mul: {price: 0.9}}
)
// 期望：{ acknowledged: true, matchedCount: 3, modifiedCount: 3 }

// 复核
db.books.find({category: "数学"}, {_id: 0, title: 1, price: 1})
// 期望：费马大定理 40.5、数学之美 32.4、哥德尔证明 43.2
```

> ⚠️ 副作用：改完价格后，Q1（price > 80）的结果**可能变化**。
> 所以查询必须全部做完再改数据。
>
> ⚠️ `$mul` 会产生浮点数，40.5 是精确的，但 36×0.9=32.4 也是精确的。
> 如果乘 0.85 可能出现 `32.399999999999999`，必要时用 `$round` 处理。

### U3 为图书新增字段并自动记录当前时间（`$currentDate`）

```javascript
// 先看有没有这个字段
db.books.findOne({isbn: "9787115428028"}, {_id: 0, title: 1, last_updated: 1})
// 期望：没有 last_updated 字段

// 执行更新
db.books.updateOne(
  {isbn: "9787115428028"},
  {$currentDate: {last_updated: {$type: "date"}}}
)
// 期望：{ matchedCount: 1, modifiedCount: 1 }

// 复核
db.books.findOne({isbn: "9787115428028"}, {_id: 0, title: 1, last_updated: 1})
// 期望：last_updated: ISODate("2026-10-21T...")
```

> 💡 `$currentDate` 的两种类型：
> - `{$type: "date"}` → 存 ISODate（推荐，能参与日期运算）
> - `{$type: "timestamp"}` → 存 BSON Timestamp
>
> 也可以简写 `{$currentDate: {last_updated: true}}`，默认就是 date。

## 五、删除操作 D1—D3

### D1 删除一条已归还的借阅记录（`deleteOne` + `$eq`）

```javascript
// 先预览：有多少条已归还
db.borrow_logs.countDocuments({status: "已归还"})

db.borrow_logs.deleteOne({status: {$eq: "已归还"}})
// 期望：{ acknowledged: true, deletedCount: 1 }

// 复核
db.borrow_logs.countDocuments()
// 期望：65（原 66 - 1）
db.borrow_logs.countDocuments({status: "已归还"})
// 期望：38
```

### D2 清理逾期未还的借阅记录（`deleteMany`）

> ⚠️ **这是最危险的一步，必须先预览再删**

```javascript
// ===== 第一步：执行前预览（必截图）=====
db.borrow_logs.countDocuments({status: "逾期"})
// 期望：13

// 看具体是哪些
db.borrow_logs.find(
  {status: "逾期"},
  {_id: 0, reader_card: 1, book_isbn: 1, borrow_date: 1, return_date: 1, status: 1}
)

// 重要发现：这 13 条全都有 return_date
db.borrow_logs.countDocuments({status: "逾期", return_date: {$exists: true}})
// 期望：13

// 严格按"未归还"筛选（无 return_date）的结果
db.borrow_logs.countDocuments({status: "逾期", return_date: {$exists: false}})
// 期望：0  ← 说明这题业务描述与数据不符

// ===== 第二步：执行删除 =====
db.borrow_logs.deleteMany({status: "逾期"})
// 期望：{ acknowledged: true, deletedCount: 13 }

// ===== 第三步：复核 =====
db.borrow_logs.countDocuments()
// 期望：52（65 - 13）

// 剩余状态分布
db.borrow_logs.aggregate([
  {$group: {_id: "$status", count: {$sum: 1}}},
  {$sort: {count: -1}}
])
// 期望：已归还 38、借出 14
```

> ⚠️ **数据矛盾**：13 条 `status: "逾期"` 的记录**全部带 `return_date`**，
> 实际语义是"逾期后已归还"，而不是任务书说的"逾期**未还**"。
> 若严格按"未归还"（`return_date` 不存在）筛选，结果是 **0 条**，无法完成 D2。
>
> **处理方式**：按 `status` 字段删除，并在预览截图中注明这个差异。
> 这是报告「问题与核对」章节的绝佳素材。

### D3 整体替换某位读者的信息（`replaceOne`，保留 `_id`）

```javascript
// 先看原数据
db.readers.findOne({card_no: "R20240016"})
// 期望：{
//   _id: ObjectId('...'),
//   card_no: 'R20240016',
//   name: '何伟',
//   college: '管理学院',
//   email: 'hewei@example.edu',
//   phone: '15300153000',
//   level: '普通',
//   register_date: ISODate(...)
// }

// 执行整体替换（保留 _id）
db.readers.replaceOne(
  {card_no: "R20240016"},
  {
    card_no: "R20240016",
    name: "何伟",
    college: "信息工程学院",       // 改了学院
    email: "hewei_new@example.edu", // 改了邮箱
    phone: "15300153999",          // 改了电话
    level: "高级",                  // 改了等级
    register_date: new Date("2024-09-19T00:00:00.000+08:00"),
    fav_categories: ["计算机", "数学"]  // 补充了原本缺失的字段
  }
)
// 期望：{ matchedCount: 1, modifiedCount: 1 }

// 复核：_id 不变，其他全换了
db.readers.findOne({card_no: "R20240016"})
```

> ⚠️ `replaceOne` 是**整体替换**，不是局部更新。
> 新文档里**没有写的字段会全部丢失**（除了 `_id` 自动保留）。
> 所以必须把 `card_no`、`name` 这些关键字段重新写一遍，否则读者记录会断链，A7/A8 关联就找不到了。

## 七、执行顺序与结果对照（报告必写）

| 阶段 | 操作 | 对后续的影响 |
|---|---|---|
| ① | Q1—Q16 全部查询 | 记录**基线**条数 |
| ② | U1 库存 -5 | **Q2（stock<10）会变** |
| ③ | U2 价格 ×0.9 | **Q1（price>80）可能变** |
| ④ | U3 加字段 | 无影响 |
| ⑤ | U4 删 tags | **Q11 12→11、Q12 17→16** |
| ⑥ | D1 删 1 条 | borrow_logs 66→65 |
| ⑦ | D2 删 13 条 | borrow_logs 65→52 |

**结论：必须先跑完全部查询，再动数据。** 报告里要把这个顺序写清楚，否则条数对不上会被判错。

## 八、排错清单

| 报错 | 原因 | 解决 |
|---|---|---|
| `$size must be a whole number` | `$size` 写了范围 | 只能写精确整数 |
| `Cannot do exclusion on field ... in inclusion projection` | 投影混用 1 和 0 | 除 `_id` 外只能全 1 或全 0 |
| `not authorized on library` | 用 libReader 做写操作 | 换 libWriter |
| `modifiedCount: 0` | 条件没匹配到，或值本来就相同 | 检查条件；`$unset` 对不存在字段也返回 0 |
| `E11000 duplicate key` | isbn 唯一索引冲突 | 换一个不重复的 isbn |
| `Cannot perform an update on a time-series` | 在 borrow_logs 上用 update | 时间序列只支持 insert，不能改已有文档 |
